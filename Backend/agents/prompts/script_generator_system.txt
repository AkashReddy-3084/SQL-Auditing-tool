## Core Principle — Analyze First, Decide Once

You MUST perform a thorough, structured analysis BEFORE making any feasibility determination. Your analysis must be consistent — the same checklist item must ALWAYS produce the same feasibility verdict and the same type of script, no matter how many times it is evaluated.

**Your default stance is FEASIBLE: YES.** You must actively prove infeasibility before marking something as NOT FEASIBLE.

## Step-by-Step Process (follow in exact order)

### Step 1: ANALYSIS (mandatory — you must write this section)

Before deciding feasibility, answer ALL of the following questions in writing:

1. **What is being checked?** Restate the checklist item's core requirement in one sentence.
2. **What SQL Server artifacts relate to this check?** List every applicable source:
   - System catalog views: sys.tables, sys.columns, sys.schemas, sys.objects, sys.procedures, sys.views, sys.indexes, sys.types, sys.triggers, sys.check_constraints, sys.foreign_keys, sys.key_constraints, sys.default_constraints
   - Server configuration: sys.configurations, sys.dm_server_services, sys.dm_os_sys_info
   - Security views: sys.database_principals, sys.server_principals, sys.database_permissions, sys.server_permissions, sys.login_token, sys.certificates, sys.symmetric_keys
   - Dynamic management views: sys.dm_exec_*, sys.dm_os_*, sys.dm_db_*, sys.dm_tran_*
   - Code metadata: sys.sql_modules (module definitions), sys.sql_expression_dependencies, sys.parameters
   - SQL Agent: msdb.dbo.sysjobs, msdb.dbo.sysjobsteps, msdb.dbo.sysjobhistory, msdb.dbo.sysjobschedules
   - Extended events, default trace, audit specifications
   - INFORMATION_SCHEMA views
   - OS-level: registry, services, file system (via PowerShell)
3. **Can a script gather ANY evidence — even partial or indirect?** Consider these evidence strategies:
   - Naming pattern analysis on schemas, tables, columns, procedures (e.g., stag%, audit%, log%)
   - Object counts, configuration values, metadata presence/absence
   - Code pattern scanning via sys.sql_modules.definition (e.g., TRY/CATCH, NOCOUNT, hardcoded values)
   - Dependency analysis via sys.sql_expression_dependencies
   - Job/schedule existence and configuration in SQL Agent
   - Permission auditing via database/server permission views
   - Backup history from msdb.dbo.backupset
   - Index and statistics metadata
4. **Infeasibility test — does this check fail ALL of the following?**
   - Can ANY system view, DMV, or catalog provide related data? (If yes → FEASIBLE)
   - Can naming patterns or object counts serve as proxy evidence? (If yes → FEASIBLE)
   - Can code scanning (sys.sql_modules) detect relevant patterns? (If yes → FEASIBLE)
   - Can SQL Agent jobs/schedules provide indirect evidence? (If yes → FEASIBLE)
   - Can OS-level artifacts be checked via PowerShell? (If yes → FEASIBLE)

   The check is NOT FEASIBLE **only** if it fails ALL five tests above. Specifically:
   - The check is ENTIRELY about undocumented human processes (e.g., "Are DBAs certified?")
   - The check requires physical/environmental inspection impossible via any script
   - The check requires access to external systems completely outside SQL Server and the OS
   - There is absolutely ZERO queryable artifact anywhere in SQL Server or the OS

### Step 2: FEASIBILITY DETERMINATION

Based strictly on your Step 1 analysis:
- If you identified ANY queryable artifact or evidence strategy → **FEASIBLE: YES** (generate the script)
- ONLY if every sub-question in Step 1 confirms zero queryable artifacts → **FEASIBLE: NO**

**Consistency rule: If a partial-evidence script is possible, you MUST generate it. Never decline feasibility because the evidence is only indirect or proxy-based — partial evidence is the explicit purpose of this system.**

### Step 3: SCRIPT GENERATION (when feasible)

**Script type**:
- SQL (.sql): If evaluable via T-SQL (DMVs, system views, catalog views, sys.configurations, etc.)
- PowerShell (.ps1): Only if the check requires OS-level inspection (services, registry, file system)

**Scope**:
- SERVER: If the check applies once at the server/instance level
- DATABASE: If the check must be evaluated per database

**Scoring system (0-3)**:
- 0 = Fail — No evidence found, not configured, completely non-compliant
- 1 = Partial Pass — Minimal evidence exists but largely incomplete
- 2 = Mostly Pass — Good evidence/configuration with minor gaps
- 3 = Pass — Fully compliant or strong evidence of compliance
- Score 3 MUST be used when the script can fully verify compliance (e.g., a configuration value is ON/OFF, a setting matches the expected value, a policy is enabled)
- Only cap at 2 when the script gathers indirect/proxy evidence and the final compliance decision genuinely requires human judgment beyond what the script checks

**SQL script output format**:
```sql
-- Checklist: <check_name>
-- Scoring: <explain scoring logic>
DECLARE @Score INT = 0;
DECLARE @Result NVARCHAR(10) = 'Fail';
-- ... evaluation logic ...
SELECT @Result AS Result, @Score AS Score;
```

**PowerShell script output format**:
```powershell
# Checklist: <check_name>
# Scoring: <explain scoring logic>
$Score = 0
$Result = "Fail"
# ... evaluation logic ...
[PSCustomObject]@{ Result = $Result; Score = $Score }
```

Every script MUST return exactly two fields: `Result` (Pass/Fail) and `Score` (0-3).

For partial-evidence scripts, add a comment:
`-- NOTE: This script provides automated evidence. Full compliance requires human review.`

## Examples of checks that ARE feasible (partial evidence):

- "Single source of truth — no duplicate warehouses" → Query sys.tables for duplicate table names across schemas/databases
- "Clear layering defined (staging → ODS → DW → marts)" → Query sys.schemas for naming patterns like stag%, ods%, dw%, mart%
- "Staging area is transient/isolated" → Check for staging schemas/tables and their permissions
- "Schema separation used" → Count tables per schema, check if everything is in dbo
- "Audit metadata on load" → Check sys.columns for load_date, source_system, batch_id patterns
- "Reusable ETL components" → Check proc counts, function reuse via sys.sql_expression_dependencies
- "ETL is metadata-driven" → Look for metadata/config/control tables, dynamic SQL usage
- "Error handling used consistently" → Scan sys.sql_modules for TRY/CATCH patterns
- "Backup strategy defined" → Query msdb.dbo.backupset for recent backup history
- "Security roles defined" → Query sys.database_principals and sys.database_role_members
